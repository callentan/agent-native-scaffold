- Added `.github/utilities/log_interaction.py`, `summarize_usage.py`, and `tests/test_interaction_log.py`. - Added the blank field table [`_templates/reports/ai-interaction-log.csv`](../_templates/reports/ai-interaction-log.csv). The program refuses to write to it directly as an active ledger.
- Updated the [tool contract and navigation](../.github/utilities/README.md#interaction-ledger), [development commands](../docs/development.md#maintenance-tools), [AI tooling boundaries](../docs/ai-tooling.md#interaction-ledger), and the root README navigation; updated the current Task18/Task12 status in the [plan](../docs/plan/2026-10-14-ddd-functional-alignment.md#task18), the [enhancement specification](../docs/design/ddd-functional-alignment.md), and the roadmap.
- The summary uses a stable, adjacent, empty `.lock` sidecar; on Windows fixed local drives, cooperating processes are serialized with a one-byte `msvcrt` byte-range lock. The lock sidecar is kept, and suspected stale locks are not cleaned up. Only these local-path semantics on the local machine are supported; no durability is claimed for network, cross-host, or synchronized directories.
- File identity and raw bytes are checked before and after writing to prevent loss of owner content. When a partial I/O failure is simulated, both append and summary output keep the actual partial bytes and return `recovery_required`; nothing is silently truncated, overwritten, or deleted, and recovery requires a manual check first.

## Task18 fix1/round1: fixes for three Important findings

The fix baseline is the local Task18 commit `be2872d06fdadcf51ca2ea36ef984dab3347842f`, with a clean working tree/index. The user had verified the three review findings. This round changes only the local summary read/write boundaries, the Task18 pre-write attestation, the binding of the summary output's parent directory, the related tests, and the directly affected contract/navigation; it does not change Task12 or connect to providers/billing.

- By default, the `summarize_usage` API/CLI neither creates nor reads the `.lock` sidecar and writes no directory entries; it confirms a stable source snapshot with two exact byte reads plus file identity/size/time attributes. Concurrent changes/partial writes return `OWNER_BYTES_CHANGED`; a stable but corrupt CSV still fails explicitly.
- Appending and creating a new summary file require explicitly passing `attest_local_storage=True` or the CLI flag `--attest-local-storage`. Without it, `WRITE_ATTESTATION_REQUIRED` refuses before the lock/output is created. The attestation is a caller declaration, not OS/vendor proof, and no cloud-sync vendor is probed.
- An explicit output first pins the Windows directory-chain handles and then creates the file relative to the leaf directory handle with `NtCreateFile` `FILE_CREATE`/no-reparse semantics; after creation it re-verifies the directory identity and the ledger source bytes. If the path is replaced by a real junction after the initial check, creation is refused; if the source/parent directory identity changes after the output is created, the error provides the new file's handle/file identity, and the file is kept for manual recovery rather than deleted automatically.

The scope is limited to the Important finding: when native `NtCreateFile(FILE_CREATE)` succeeds but `msvcrt.open_osfhandle` or the first `os.fstat` on the output fd fails, the output is already on disk, so the error must be recovery-required and carry a stable file identity.

The new tests ran RED first on a real local fixture: a wrapper failure is injected after the native file has been created; then a first-`os.fstat` failure is injected on the actual summary fd (identified exactly by the fd returned from the real `open_osfhandle`, without affecting the lock fd). The output is kept, not deleted; the API and CLI return the recovery flag and identity.
