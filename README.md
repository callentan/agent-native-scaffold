# AI Native 开发脚手架：研究与设计

**状态：设计提案，尚未实施。研究日期：2026-10-12。**

建议最终建立一个独立仓库，暂名 `agent-native-scaffold`。它不是另一套提示词合集，也不是重新开发一个 AI IDE，而是：

> **让现有 coding agent 在明确的业务事实、执行契约、隔离环境和验收机制下，持续接手开发任务的工程底座。**

本目录目前只包含研究、设计和计划；没有初始化 Git 仓库，没有实现 CLI、运行时、模板代码或流水线，也没有修改参考仓库。

## 先看结论

参考工程最值得保留的是 **DDD 领域事实、V-model 追溯、工作流级 skills、版本化依赖和人工决策边界**。需要补足的不是更多“角色 agent”，而是把文字约定变成机器能执行的约束：

| 需要具备的能力 | 设计方向 |
|---|---|
| 看懂项目 | 简短的 `AGENTS.md` 导航、结构化项目清单、按任务加载的上下文 |
| 知道能做什么 | 有类型的输入输出、范围限制、前置条件、受保护审批 |
| 独立完成开发 | 复用现有 agent，完成代码、测试、运行验证、修复和 PR 交付 |
| 中断后继续 | 持久任务状态、检查点、输入版本和幂等恢复 |
| 证明完成 | 验收项 → 测试标识 → 实际执行结果 → 提交版本的证据链 |
| 长期维护 | 同一版本发布的规则、skills、模板、校验器，以及可预览的升级 |

**推荐形态：一个独立框架仓库 + 可选的 DDD/V-model 方法包 + 技术栈包 + agent/代码托管平台适配器。**

首个试点建议贴近已有工程：`.NET 服务 + DDD/V-model + Azure DevOps`。通用核心不依赖 Device Registry 的业务，也不把医疗监管流程强加给所有项目。首版以“自动交付待审 PR”为边界，不默认自动批准需求、自动合并或部署生产。

## 如何理解“完全托管”

不是保证模型理解所有隐含知识，而是让 agent 能明确回答：**事实在哪里、当前任务是什么、允许改哪里、怎样运行、怎样证明完成、何时必须停止。**

在已批准范围内，agent 可以连续执行开发闭环；遇到业务歧义、架构边界、风险控制、权限升级或证据缺失时，必须显式升级处理。人类保留目标、规则和高风险决策的所有权，不必人工操纵每一次文件修改。

## 资料使用边界

本设计包含内部 Azure DevOps 仓库的结构和研究摘要，应按内部材料管理。原文抽样保存在本次会话的研究证据区，没有复制到本目录。未来若建立公开仓库，应只迁入通用设计及合成示例，并先确认现有框架、名称、模板和代码的授权。

文档中的目录树、命令和数据结构均是**未来设计示意**，不代表这些能力已经实现。性能、成功率和工期数字均为待验证的规划目标，不是研究实测结果。
