# 待决策项、风险与范围边界

这些决策供开始实施前的 P0 评审使用。推荐项不代表用户已经授权创建仓库、复用代码、扩大权限或自动发布。

## 1. 待确认的关键决策

| ID | 决策 | 当前推荐 | 未确认时的影响 |
|---|---|---|---|
| D01 | 独立仓库名称、托管位置、可见性、所有者 | 暂名 `agent-native-scaffold`；先按内部材料治理 | 不创建或公开远端仓库 |
| D02 | 与 Tantu/现有框架的关系及复用授权 | 独立核心，兼容现有工件；先复用思想，代码和模板另核授权 | 不搬运源码、模板或沿用品牌 |
| D03 | 首个技术栈和试点任务 | .NET 服务；从已有模式选一个批准的小任务 | 不扩展到多语言脚手架全集 |
| D04 | 首个 agent 运行时 | 优先验证组织允许的 Copilot CLI；实际能力不足时评审替代项 | 不假设可直接调用产品未提供的接口 |
| D05 | 首个托管平台及身份方案 | Azure DevOps；最小权限服务身份，发布令牌在 worker 之外 | 不自动创建 PR、推送或申请权限 |
| D06 | 自主边界 | 范围内编码/测试/修复自动，交付到待审 PR | 不自动合并和部署 |
| D07 | 医疗/监管适用性与资格要求 | 由实际产品和风险负责人确认，不由 agent 分类 | 不宣称 regulated-ready 或合规 |
| D08 | 工具链、运行环境、网络和资源预算 | 锁定一组环境；隔离运行，预算可配置且经批准 | 环境不足时不启用 managed 模式 |
| D09 | 审批和证据系统 | 优先复用托管平台身份记录与受信 CI artifacts | 不把 Markdown 签名当认证 |
| D10 | 旧文档状态、ID 和摘要迁移 | 显式适配，先只读报告，再分批迁移 | 不默认改名、不猜状态、不批量提升批准 |
| D11 | 外部 ADR、QMS、知识快照的访问与留存 | 授权连接器或批准的版本化摘要 | 不擅自复制受控资料到新仓库 |

## 2. 当前方案明确作出的设计取舍

| 选择 | 原因 | 代价 |
|---|---|---|
| 独立单仓统一发布核心/规则/skills/模板 | 避免多依赖 HEAD 组合不可验证 | 框架维护者需要承担兼容矩阵 |
| 不重写现有 agent 工具循环 | 降低维护和模型绑定成本 | 需要验证运行时能力，不能承诺所有特性一致 |
| 通用核心 + DDD 方法包 | 继承现有资产，又不强迫所有业务采用重流程 | 工件映射必须清晰，不能靠路径硬编码 |
| 单 worker 起步 | 先解决闭环和恢复，再解决规模 | 初期不追求最大吞吐量 |
| 审批和执行状态分离 | 避免自行写 Approved/Done 就绕过流程 | 多一份可信审批关联 |
| 证据由实际执行生成 | 避免文档和测试文件存在即宣称完成 | 需要真实环境和结果解析 |
| 自动生成矩阵与摘要 | 降低重复维护与漂移 | 必须清晰定义唯一权威数据 |
| 初始只交付待审 PR | 先积累可靠性和边界数据 | 暂不追求彻底无人值守合并 |

## 3. 主要风险与处置

| 风险 | 触发信号 | 处置 |
|---|---|---|
| 变成文档工厂 | 工件越来越多，实际交付仍全靠人工 | MVP 必须包含代码、测试、运行验证和恢复闭环 |
| 成为过度庞大的平台 | 先建调度集群、知识库、Web，再找使用场景 | 用一个 CLI 包和单主状态先验证价值 |
| 源资料没有单一权威 | Markdown、YAML、工单互相矛盾 | 配置 authority mapping，生成投影，不静默选择 |
| prompt 与治理政策矛盾 | 一处要求人工批准，一处允许自动批准 | 确定性策略优先；矛盾输入阻塞并显式评审 |
| 把假设当事实 | 反向提取的高置信度输出直接参与开发 | confidence 与 approval 分离；保留来源和未决项 |
| 测试被优化成“必过” | 删除检查、降低覆盖、验收语义漂移 | 受保护验收基线、差异检查、独立审阅与故障用例 |
| 外部权限和资料泄露 | 令牌进入 prompt、日志或候选代码环境 | worker 最小权限、凭据隔离、脱敏和出站限制 |
| 并发覆盖 | 共享分支、共享输出目录、共享数据库 | 独立工作区及资源命名，协调器领取，冲突停止 |
| 恢复重复副作用 | 重复 PR、重复发布、重复同步 | 幂等键、远端查询、因果记录，不盲重试 |
| 版本升级破坏业务 | 自动更新所有 submodule 或重渲染已有代码 | 锁版本、三方迁移预览、项目文件保护 |
| 跨仓库循环 | 实现摘要和领域 pin 相互触发更新 | 区分事实提交与报告提交，固定基线和用途 |
| 伪合规 | 安装 profile 后就声称满足法规 | 专业评审、明确能力边界，不做认证承诺 |
| 运行时或供应商变化 | 非交互模式、输出、定价、权限行为变化 | 能力检测、版本记录、契约测试和回归评估 |
| 模型不确定性 | 同输入不同结果、长任务漂移 | 小任务、有限重试、真实验收、评估而非宣称确定性 |

## 4. 与参考工程不同之处需要明确批准

新方案不是照搬现行流程。以下变化是为了本次目标而提出，不能伪装成已有约定：

- 从“代码生成不负责测试”改为“托管交付必须包含测试实现和执行证据”。
- 从“在提示词中要求只读，同时更新 submodule”改为单独的报告回传协议。
- 从多个共享仓库独立组合改为统一版本发布；对旧项目仍提供兼容读取。
- 从本地文本审阅标记改为外部可验证、与内容版本绑定的审批。
- 从固定角色主流程或无差别自动批准，改为工作流节点与风险受控自治。
- 将通用方法、领域方法、assurance 和执行模式拆开，而不是给所有项目一种治理重量。

## 5. 对用户目标的覆盖

| 原始目标 | 本轮设计覆盖 |
|---|---|
| Agent 能看懂工程 | 短入口、项目清单、权威来源、上下文包、冷启动评估 |
| Agent 可以托管开发 | 状态机、隔离运行、代码与测试闭环、恢复、发布与升级 |
| 最终成为独立 repo | 框架与业务仓库蓝图、发布单元、授权及建仓前置决策 |
| 先研究现有体系 | 八仓目录、固定版本、关键契约、实际纵向样本和版本差异 |
| 参考公开主流模式 | 九项一手来源及适用/不照搬的边界 |
| 本轮不要实现 | 当前目录只有研究和设计文档；实现目录和命令仅为示意 |
| 在当前路径组织中间资料 | README + research/design/plan 文档结构 |

## 6. 本轮明确没有做的事

没有修改 Azure 仓库、初始化 Git、创建远端 repo、安装脚手架、实现 CLI、运行业务部署或改变权限。没有把参考仓库中的“通过”“批准”“覆盖率”当作已复核的实际结果。

本轮完成的产物是可供下一轮决策与实施使用的研究和设计包；是否进入 P0 之后的代码阶段，仍以用户后续授权为准。
